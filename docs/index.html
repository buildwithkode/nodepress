NodePress Headless CMS

An enterprise-grade, self-hosted headless content management system. Design flexible schemas, manage multi-environment workflows, upload assets, and consume content through auto-generated REST APIs, GraphQL, and real-time WebSockets.

Docs for NodePress 1.7. New in 1.7: field data migrations, conditional fields, reusable components, custom roles, the WordPress importer, OpenAPI + Swagger UI, schema:pull/diff/push, live preview, framework starters, redirects and the plugin directory. The admin panel in your install has the same docs at /docs.

Installation — Step by Step

Follow these steps in order. Each step takes only a few minutes. NodePress runs locally on your machine or on any server with Node.js 18+ and PostgreSQL (or Docker).

Already have some tools installed?

Run these commands in your terminal to check. If you see a valid version, you can skip that step.

1

Install Node.js

Already installed? Run node -v — if it shows v18 or higher, skip to Step 2.

Node.js is the engine that runs NodePress. Download and install version 18 or newer (LTS recommended).

Content Types Builder

Content Types are the data blueprints (schemas) for your content (e.g., Blog Posts, Products, Authors, Pages). NodePress automatically provisions REST endpoints and GraphQL queries for every content type you build.

• Display Names & Slugs: Automatically formats snake_case database identifiers into human-friendly titles.

• Dynamic Endpoints: Creating blog_posts creates /api/blog-posts instantly.

• Method Locks: Choose which HTTP methods (GET, POST, PUT, DELETE) are exposed per collection.

• Preview URL: an http(s) template for the page that shows an entry on your site, with {slug}, {locale} and {token} (a signed 1-hour preview token) — e.g. https://www.example.com/blog/{slug}?preview={token}. Up to 2,048 characters, no placeholders in the host. It drives the editor's Live pane and the automatic slug-change redirects.

• Export / Import JSON: bundles carry the content types, their Preview URLs and the components and choice lists they use (all of them on a full export); import writes components and choice lists first. GET /api/content-types/export / POST /api/content-types/import accept an admin JWT (export: editors too) or an X-API-Key with all access to * — other keys get 403, and key imports are audited as api-key:<name>.

Conditional fields — “Show only if…”

Any field can carry a condition so it is shown only when a sibling field (same level: top-level fields, or the same repeater row, group or flexible block) matches. Set it with Show only if… in the content type editor. A hidden field is never required — in the admin or the API — and a field whose condition field is hidden is hidden too.

Reusable Components

A component is a named set of simple fields (an SEO block, a call-to-action, a person's details) defined once under Content → Components (/components) and reused anywhere. Click Add component in the content type editor and pick one of four ways to use it:

UseWhat you getEntry data
OneA group field with options.component — one nested object."seo": { "meta_title": "…" }
ManyA repeater field with options.component — a list of items."links": [{ "label": "…", "url": "…" }]
InlineThe component's fields go straight into the content type, at the top level, with no wrapper object."gender": "male"
Flexible layoutA layout of a flexible field whose fields come from the component."body": [{ "_layout": "cta", … }]

• The server copies the component's fields into the content type on every save (group/repeater sub-fields, layout fields or the inline fields), so the API output is that of ordinary fields. Never edit the copies — edit the component.

• Inline keeps entry data flat: a type using a person_details component inline stores { "full_name": "Ada", "gender": "male" }. A content type can use a component inline only once, and its field names must not clash with the type's other fields (400). The editor shows the inline fields as one read-only From component block that moves as a unit.

• Flexible layouts: click Add layout from component in a flexible field; component layouts mix freely with hand-made ones.

• Editing a component updates every content type using it, in all four ways (each gets a schema version); the response lists updatedContentTypes and propagationErrors.

• Renames move data: PUT /api/components/:id takes fieldMigrations with component field names, applied as <field>.<name> (group/repeater), <name> (inline) or <field>.<layout>.<name> (flexible layout). The Components page sends renames for you; retyped or removed component fields keep their data.

• Simple fields only. Unknown component → 400; deleting one in use → 409. usage[] lists each use with its type: group, repeater, inline or layout.

• API: GET /api/components, GET /api/components/:id (with usage) for signed-in users; POST / PUT / DELETE for admins.

Choice Lists

A choice list is a shared set of options for select fields — gender, country, department — kept in one place so every content type offers the same choices. Manage them under Settings → Choice lists (/choice-lists, admin only). Each choice has a value (what entries store) and an optional label (what editors see). A select field takes its choices either typed in (options.choices) or from a list (options: { "choiceList": "gender" }).

Example — a Gender list used by several content types:

Put the field in a component used inline and every content type that includes it gets the same gender field at its top level — the entry still stores "gender": "male".

• On every save the server copies the list into the field: values into choices, labels into choiceLabels ({ value: label }, only where they differ). This covers top-level fields, repeater/group sub-fields, flexible layout fields and components.

• The list editor adds choices one by one, pastes several at once (one per line: Label or value | Label) and reorders by drag.

• Editing a list updates every content type and component that uses it. Removing values reports how many entries still hold them (removedValuesInUse); those entries fail validation on their next save until a new value is picked.

• A list in use can't be deleted (409). Up to 1,000 choices; values unique, non-empty, ≤ 200 characters.

• Schema export/import bundles and schema:pull / schema:push carry choice lists. choice-lists is a reserved content type name; changes are audited as choice_list.

Schema Changes & Data Migrations

Entry values live in one JSON column, so a schema change alone leaves data behind: a renamed field keeps its values under the old key, a retyped field keeps old-type values. When you save a content type whose changed fields hold data, the admin shows a confirm dialog with the impact (entries touched, values a conversion would drop) and lets you migrate the data with the schema.

• Paths: title (top level), seo.meta_title (group sub-field, or repeater sub-field in every row), blocks.hero.heading (a field of one flexible layout). Nested paths use the container's new name; a rename stays in the same group, repeater or layout.

• Order: top-level renames, nested renames, conversions (by new path), drops.

• The preview's removedNested lists fields removed from inside a group, repeater or layout that still exists; the dialog offers to drop their data. The editor tracks sub-field renames and sends them.

• Renaming a flexible layout isn't migrated — rows keep the old layout name.

• Conversions: anything → json; text ↔ richtext; text/number/boolean → text or select; multi-select → first value; text → number (numeric strings) or boolean (true/yes/1/on, false/no/0/off). Unconvertible values are removed and counted as lost in the preview.

• Reverse relation fields (mappedBy) follow renames. Old entry versions keep their old shape.

Content Languages (i18n)

Every entry has a BCP 47 locale; entries with the same content type + slug are translations of each other. Admins pick the enabled languages and the default under Settings → Languages (GET /api/locales is public, PUT is admin).

Single reads set Content-Language. Admin interface languages are separate: the admin panel is available in English, French, German, Spanish, Portuguese, Italian, Dutch, Japanese and Simplified Chinese — each person picks theirs in the top bar.

Relations & Two-way Links

Relation fields store the target's publicId; ?populate=author,author.company inlines them (3 levels, one batched query per level). A relation with options.mappedBy is a reverse field: it stores nothing and lists the entries whose forward field points here (newest 100, read-only).

Security (1.7)

Populated entries are filtered by the related content type's field readRoles for the caller, and their contentType is trimmed to { id, name, displayName }. Public reads only populate published entries.

Every team member can activate TOTP-based 2FA (Google Authenticator, Authy) from their user profile with backup recovery codes.

Custom roles

Team → Roles (/users/roles, admin only) adds roles such as translator. A custom role is based on editor, contributor or viewer: it gets that role's admin access, and its content permissions start as a copy of the base role's, narrowed per content type in the permissions matrix. Names are snake_case and immutable; a role still assigned to users can't be deleted (409 with userCount). Users are invited with custom roles like built-in ones; /api/auth/me returns role (base) and customRole. OIDC_ROLE_MAP may target custom roles. Field readRoles/writeRoles may list custom role names; a rule matches the custom role or its base role, and admins always pass (the field matrix has a column per custom role). Changing baseRole swaps the role's * row to the new defaults unless you customised it — then it's kept and the response's warnings says so. Reset to defaults keeps custom roles and restores their * rows from their base role.

Sessions, Auth & Password Reset

NodePress utilizes a dual-tier token architecture designed for high security, seamless session persistence, and robust lockout recovery.

Field-Level Permissions

Under Users → Permissions → Field Permissions, lock down individual fields per role:

Read AccessHide sensitive fields (internal margins, SEO overrides, admin notes) from specific roles.
Write AccessPrevent non-admins from modifying protected fields (e.g. author verification badges).

Changed in 1.7 — content permissions on every write path

• The public write API (POST/PUT/DELETE /api/:type) now checks the role's content permissions for JWT callers too. Creating a published entry (the default) or promoting one needs publish — a contributor's JWT must send status: "draft".

• POST /api/entries checks the entry's own content type, not the * row. A role that no longer exists is treated as a viewer.

• ?populate respects the related type's field readRoles.

• Bulk routes check every affected content type (bulk-publish / bulk-promote to published → publish, bulk-delete → delete, others → update). Any denial is a 403 with forbiddenContentTypes and nothing changes.

• GraphQL createEntry, updateEntry, deleteEntry, restoreEntryVersion and bulk* mutations run the same per-type checks; admin entry queries and mutations apply the caller's field rules.

Audit Logging

All administrative actions (entry modifications, schema updates, logins, role changes) are recorded immutably with timestamp, actor email, IP address, and before/after state diffs.

Filter by resource: entry, content_type, user, api_key, form, media, plugin, settings, release, role, redirect, component, choice_list, import. Entries are pruned after AUDIT_LOG_RETENTION_DAYS (default 90).

Webhooks & Dead-Letter Queue (DLQ)

Webhooks automatically POST JSON events to external services whenever content or media changes. Signed with HMAC-SHA256 (X-NodePress-Signature).

• Automatic Retries: 3 attempts with exponential backoff (Immediate, +5m, +30m).

• Dead-Letter Queue (DLQ): Failed deliveries are archived in the DLQ with full payload & error headers.

• 1-Click Re-Delivery: Re-dispatch any failed delivery directly from the admin UI or via POST /api/webhooks/deliveries/:id/retry.

Plugin Architecture & UI Manager

NodePress includes an enterprise-grade extension engine with an internal lifecycle hook bus (PluginHookBus) and a visual Admin Management UI (/plugins). Admins can enable/disable plugins without a restart and configure custom settings via a slide-out settings drawer.

🛡️ Isolated Hook Errors

In legacy CMS engines (like WordPress), a single unhandled error or slow database query in a third-party plugin can crash the entire web server or cause a White Screen of Death (WSOD). NodePress isolates plugin hook errors:

  • Layer 1 Capability-Based Permissions: Plugins must declare explicit permissions (e.g. ['entries:read', 'entries:write']). If an unauthorized action is attempted, execution is blocked and logged.
  • Layer 2 Isolated Error Boundaries: Every hook and filter is wrapped in isolated error boundaries. If a plugin throws an uncaught exception, NodePress catches the error, logs the trace, and continues serving requests smoothly without crashing.
  • Layer 4 Hard 5-Second Timeouts: All asynchronous plugin hooks are wrapped with a 5000ms timeout guard (Promise.race). Slow or hanging external HTTP calls will never lock up CMS transactions.
  • 0-Downtime Dynamic Toggling: Any misbehaving plugin can be instantly deactivated live from the /plugins UI with 1 click.

Redirects

Content → Redirects (/redirects, editors and admins) manages 301/302/307/308 and 410 (gone) rules. Your site asks NodePress: GET /api/redirects/resolve?path=/old-page → { to, statusCode } or 404 (public; cached 5 min, Cache-Control: max-age=60).

• Hits are counted per rule, buffered and written every 10 s; opening the admin list writes this instance's buffered hits first.

• Matched on the path only — lowercased, trailing slash removed. A query string matches only if the rule's from has one; otherwise it is carried over to the target.

• Targets are a path or an http(s) URL; a 410 has no target. Loops and chains longer than 5 hops are refused.

• CSV import/export (from,to,status, ≤10,000 rows, all or nothing, dry run).

• Automatic 301 when the slug of an entry that has ever been published changes — old path from the Preview URL (when it has {slug}), else /<type-kebab>/<slug>, with a /<locale> prefix for non-default languages. REDIRECTS_ON_SLUG_CHANGE=false turns it off.

JavaScript / TypeScript Client

@nodepress/client is a zero-dependency typed client for the public API (Node 18+, browsers, edge). Pair it with npx nodepress generate:types.

Live Preview

With a content type's Preview URL set, the entry editor gets a Live toggle: your site in a resizable pane (device widths, reload, new tab), the preview token refreshed automatically and every edit streamed as you type. Clicking an outlined element focuses its field. The entry must be saved once — on the new-entry page, Save draft & preview (types with a Preview URL) saves a draft and opens the editor with the Live pane on (?live=1).

Framework Starters

starters/ in the repo has minimal blogs on @nodepress/client: nextjs (App Router, draft mode + live preview), astro (static build) and nuxt (server-rendered, API key stays server-side). Each has cursor pagination, sanitized richtext, resized cover images and ?populate=author.

Schema as Code (CLI)

Keep the content model in git. Connect with NODEPRESS_URL + NODEPRESS_TOKEN (or NODEPRESS_API_KEY, --url/--token): an np_ token is sent as X-API-Key (needs all access to *), anything else as an admin Bearer JWT.

Pull, diff and push cover content types, components and choice lists. Push creates and updates them but never deletes one that exists only on the server.

Content Releases

A release groups publish / unpublish / archive actions on many entries and applies them in one transaction — now or on a schedule (checked every minute, exactly once across instances). Manage them under Content → Releases; editors and admins. Publishing fires the usual entry webhooks and plugin hooks plus release.published; a plugin veto fails the whole release.

Starter Templates

Content Types → Start from a template creates a ready-made model — blog, agency or docs — with relations and optional sample entries. API: GET /api/templates, POST /api/templates/:id/apply { "sampleContent": false } (admin).

WordPress Importer

Settings → Import (/import, admin) takes a WordPress WXR export (≤50 MB), shows a dry-run summary, then imports in a background job.

• Posts, pages and custom post types → one content type each: title, content (richtext), excerpt, featured_image, categories/tags (JSON arrays of names), author (text), wp_id, meta (non-underscore post meta, ACF included). Reserved names get a wp_ prefix.

• Status: publish → published, draft/private → draft, pending → pending review, future → draft with publishAt.

• Existing types are reused; existing slugs are skipped unless Overwrite. Optional media import into a “WordPress import” folder (upload types only, 10 MB, public http(s) URLs only).

• On reused types, existing date/datetime fields are filled when the value is a valid date. Never imported: login accounts, spam/trashed comments, pingbacks, post_format and nav_menu terms. Multi-instance setups need a shared uploads/.

AI Assistant & MCP Server

Set ANTHROPIC_API_KEY (optionally AI_MODEL) to enable Generate with AI for content models and Draft with AI in the entry editor — suggestions fill the form, nothing is saved until you save. The CLI also ships an MCP server so assistants (Claude Desktop, Claude Code, Cursor) can read content and draft entries; read-only without a key.

Search Engine

?search= uses Postgres full-text search by default. For typo-tolerant ranking set SEARCH_DRIVER=meilisearch, MEILISEARCH_URL and MEILISEARCH_KEY (or docker-compose.search.yml), then reindex once from Settings → Email & storage or POST /api/search/reindex. Writes keep the index current via the job queue; Postgres answers when Meilisearch is down (meta.searchMode says which).

Email & Storage Settings

SMTP and file storage (local disk or any S3-compatible bucket: AWS S3, Cloudflare R2, DigitalOcean Spaces, MinIO, Backblaze B2) can be configured in the setup wizard and under Settings → Email & storage, with test buttons. Secrets are stored encrypted (SETTINGS_SECRET, else JWT_SECRET). SMTP_* / STORAGE_* env vars take precedence. Email changes apply at once; storage changes after a restart.

API Authentication & Token Guide

Do you need a token for every API request? No! For public websites and visitor frontends (Next.js, React, Astro, Vue, mobile apps, or static sites), content reading and form submissions require ZERO authentication tokens. Anyone can query published content without sending headers or secret keys.

The 3-Tier Security Architecture

Tier 1: Public Read APIs No Auth Required (Zero Token)

Used by consumer frontends to render articles, product catalogs, pages, brand settings, sitemaps, and accept contact form submissions.

GET /api/:contentType e.g. /api/posts, /api/products
GET /api/:contentType/:slug e.g. /api/posts/my-first-post
GET /api/brand Public logo, company name, theme colors
POST /api/submit/:formSlug Public forms protected by honeypot & spam shield
GET /api/sitemap.xml Auto-generated dynamic XML sitemap
Tier 2: Headless Frontends & SSG X-API-Key: np_live_...

For static site generation (Astro, Next.js SSG build step), CI/CD content sync pipelines, or external microservices that need scoped access or draft preview without managing user credentials.

Header: X-API-Key: np_live_...
Generate scoped API keys in Admin Panel → Settings → API Keys
Tier 3: Admin & Content Mutations Authorization: Bearer <JWT>

Required for creating, updating, deleting entries, uploading media assets, configuring webhooks, and inviting users. Authenticated via JWT obtained from login.

Header: Authorization: Bearer eyJhbGciOi...
NodePress admin UI rotates access tokens automatically via HttpOnly refresh cookie
